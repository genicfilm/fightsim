# Working on FIGHT SIM

Read this before changing anything. It exists so you never have to guess.

**FIGHT SIM** runs any two UFC fighters through 1,000 Monte Carlo rollouts over a
calibrated logistic fit and reports the *distribution* — and **refuses the fights
it has no edge on**. Static single HTML file, no backend, no network, no
dependencies at runtime.

`EVENT` mode runs a whole card at once and exports one scorecard with the
refusals marked, plus a JSON receipt for `ledger/`. That pairing — commit the
receipt before the card, grade it after — is the part of this project no
competitor has, and the reason the refusals have to stay honest.

---

## Build, run, test

```bash
npm run build:fightsim    # fightsim/index.html + data.json + fonts -> fightsim/FightSim.html
npm test                  # 43 assertions, drives the BUILT file with Playwright over file://
npm run shots             # 8 screens diffed against tools/baseline/ — layout regressions
npm run shots:update      # accept the current screens as the new baseline
```

- **`fightsim/index.html` is the source you edit.** `fightsim/FightSim.html` is
  generated — never hand-edit it, your change will be overwritten.
- **Always rebuild before testing.** `npm test` reads the built file, not the source.
- **Never introduce a dev server.** Under WSL2 Windows does not reliably forward
  `localhost`; the product is also required to work from `file://` with the
  network off. The test suite drives `file://` for this reason.
- `npm test` exits non-zero on failure. Treat a red suite as a blocked change.
- **Run both suites from WSL bash, never from Windows.** `tools/chromium-path.mjs`
  falls back to system Chrome/Edge, which rasterises through DirectWrite instead
  of the Playwright binary's FreeType. An external audit reported all 8 screens
  failing at up to 10.2% on that path; from WSL every screen diffs at 0.000%.
  Running `shots:update` on a Windows run bakes a foreign rasteriser into the
  committed baselines.

```bash
node tools/ledger.mjs        # grade ledger/*.json -> ledger/README.md
python3 tools/build-data.py  # also writes tools/metrics.txt (the published numbers)
```

Chromium is located by `tools/chromium-path.mjs` (Playwright cache, then system
Chrome/Edge). Set `CHROME_BIN` to override.

## The boundary: what is UI and what is not

### You may change freely

Layout, spacing, type scale, component structure, animation, the canvas
*drawing* in `simFrame` and its helpers, copy tone, responsive behaviour,
focus states, the share-card composition in `drawCard()`.

### You must not change

| Not UI | Why |
|---|---|
| `terms()`, `logit()`, `sigmoid()`, `probability()`, `diffVector()`, `weightPrior()`, `empanel()` | This is the model. Changing it changes the answer. |
| `fightsim/data.json` | Generated by `tools/build-data.py` from public UFC data. Regenerate, never hand-edit. |
| The numbers below | Measured, and now **recomputed by the build**. Do not round up, restate, or "improve" them. |
| `FREE_LBS = 20`, `PER_LB = 0.05`, `CAP = 5.0` | The cross-division prior, calibrated against 451 real division-up fights. |

### The numbers, and where they come from

`tools/build-data.py` prints all of these and writes them to `tools/metrics.txt`.
If you change the model, rerun it and copy the block it labels *THE NUMBERS THE
UI IS ALLOWED TO PRINT*. Nothing on screen may state a figure this file does not
produce — that rule is what the whole project is selling.

| | | |
|---|---|---|
| 61.2% | held-out accuracy, forced to call every fight | mean of the nine annual folds |
| **40.4% / 52.0%** | share it **refuses** (conf < 0.58), and what those realised | the refusals are measured, not a design flourish |
| **59.6% / 67.2%** | share it will call, and what those realised | this is the number the product is actually for |
| 15.6% / 76.8% | share it calls ≥0.70, and what those realised | |
| **0.230** | Brier | was published as 0.232; the build computes 0.2299 |
| **1.1 pts / 2.5 pts** | weighted ECE, and the worst single band | was published as "≤2 points in every band", which is **false** under the bands the docs describe — the 0.50–0.55 band is off by 2.45. ECE is a mean and "every band" is a max; quoting one label over both is how a claim becomes unfalsifiable |
| **3,404** | held-out **fights** | previously published as 6,808, which is the *mirrored evaluation* count. Each fight appears as A–B and B–A, and since the intercept is exactly `-0.0` the mirrored half carries provably zero information. Report fights |
| 6,457 · 2,290 · 8,880 | training bouts · fighters · career versions | |

**The feature count is derived, never typed.** It is `M.cols.length` — 34: the
32 named stat and bio columns plus elo and listed weight. The masthead used to
state a hardcoded 32 (`M.feats.length`), which excluded elo and so undercounted
by leaving out what is routinely the single largest term in the attribution
panel. The masthead, both pipeline captions and the step-01 readout all read it
off the model now, and the suite asserts the number on screen equals the number
of coefficients the model sums. Do not reintroduce a literal.

### Four product rules that outrank any design idea

1. **Never call the output a prediction, forecast, or pick.** It is a
   distribution. The footer line `NOT A PREDICTION. A DISTRIBUTION.` stays.
2. **No fighter photography, ever.** No rights exist. Licensed imagery killed
   the predecessor project. Graphic only — type, bars, cells, badges, plots.
3. **No method inflation.** It is L2 logistic regression over 34 engineered
   features. The copy is deliberately technical (Monte Carlo rollouts,
   posterior, log-odds, Brier, ECE, rolling-origin CV, binary entropy) because
   all of that is literally true. **Never write "deep learning", "neural",
   "AI", or imply a method this does not use.**
4. **Out-of-distribution adjustments stay visible.** The weight prior is printed
   on screen, listed in the attribution panel at its exact log-odds, and
   stamped on the exported card. It is never allowed to become invisible.

### The differentiator, if you are writing copy

There are three, and they are load-bearing in this order:

1. **It refuses.** Every competitor emits a confident winner on every fight;
   none of their scoring systems can even represent "no edge". This one declines
   40% of matchups, and on those it measured itself at 52.0% — under 0.55 it
   realised exactly 50.0%. **The refusals are the product.**
2. **It is line-blind.** It never sees a betting line. That is the entire
   explanation for why this is 61% and not 70%, and it is a methodological
   commitment rather than a shortcoming: odds-aware models buy roughly six
   points by reading the market back to you.
3. **Rolling origin.** Every feature is computed only from bouts that had
   already happened; a random split scores higher on the same data by leaking a
   fighter's future into their own past. *These numbers are lower because they
   are real.* **That sentence is the pitch. Do not soften it into a bigger
   number.**

**Never make a claim about a named or implied competitor.** The screen used to
read *"Fight models advertising 75% random-split their data"* — an unquantified
assertion about third parties that this repository could not substantiate, on
the one screen built to disarm a sceptic. State the mechanism, never the
accusation: a random split *does* score higher by leaking, and that is provable
here. Who else does it is not our claim to make.

## Hard runtime constraints

- **Offline.** No CDN, no external fonts, no libraries, no `fetch` to any host.
  The built file must open from disk with the network off. Fonts are inlined as
  data URIs by the build; the model and all fighters are inlined as a
  `<script id="fjdata" type="application/json">` block.
- **`tools/build-fightsim.mjs` injects at the literal string `` `<script>\nlet M=null` ``.**
  If you restructure the opening of the script tag, update the build script or
  it will fail loudly (it already checks and exits 1).
- The card is drawn by hand on Canvas 2D because html2canvas would need a CDN.
  `await document.fonts.ready` before drawing — canvas silently falls back to a
  system face otherwise and the card renders wrong.
- Respect `prefers-reduced-motion`. `CALM` is already computed; the pipeline
  compresses to ~2.6s under it. Keep that path working — the suite asserts it.

## The DOM contract

`npm test` asserts all 62 of these ids exist. You may restyle, re-nest, or
re-order any of them. **Renaming or removing one silently breaks the page.**

**Class names are not covered by anything.** `.hero` is already the tape's ELO
row (`.tr.hero`), which lives inside `#empanel` — so a new `#empanel.armed
.hero{max-height:0}` rule collapsed the ELO row to a 10px sliver and the suite
stayed green, because it asserts the row *exists*, not that it has height.
Grep before you name a new class, and prefer a descendant selector on a
container class over a bare one.

**`npm test` cannot see layout — `npm run shots` can.** That exact bug was
reinjected to check: `npm test` reported 42/42 while three screens moved by
4–12% of their pixels. Run both before you ship.

If you need to rename an id, update `fightsim/index.html` and `CONTRACT` in
`tools/test.mjs` together.

## The mark

The logo lives **once**, as an inline `<symbol id="glyph">` near the top of
`fightsim/index.html`. The masthead and the method screen reference it with
`<use>`; `drawCard()` reads the same element's `<path>` and `<rect>` attributes
and replays them into Canvas 2D. Change the symbol and every surface follows.
Do not restate the geometry anywhere — that is how a logo drifts.

- **Vector, never a bitmap.** The file must stay offline and self-contained, and
  the same mark has to hold up at 22px in the card footer and at 2160px wide.
- **Octagon = the cage. The axis is dead centre at x=50.** Fighter on the left,
  the sample on the right. That split is the product; keep it centred.
- **Monochrome.** `currentColor`, inherited from `--ink`. The wordmark used to
  be blue/red, which spent the corner distinction on the logo itself — red means
  RED CORNER everywhere else on the page.
- The oblique is `skewX(-9deg)` in CSS and the matching shear in canvas, because
  Anton ships upright only. Both must move together.

The favicon is a separate, simplified copy in the `<link rel="icon">` data URI —
the helmet does not read at 32px, so it carries the octagon, the axis and three
bars. It is the one deliberate duplication.

## Visual regression

```bash
npm run shots            # check 8 screens against tools/baseline/
npm run shots:update     # accept what is on screen now (look at it first)
```

A failure writes the shot and a red-marked diff to `tools/.shots-out/`
(gitignored). `tools/baseline/` **is** committed — a changed baseline is part of
the diff a reviewer reads, which is the point.

Three things keep it reproducible, and all three are load-bearing:

- **`Math.random` is seeded from the harness** via `addInitScript`, never in the
  product. Without it the 1,000 rollouts differ every run and every screen is a
  false positive. With it, the settled verdict diffs at 0.000%.
- **Nothing is captured mid-animation.** `stilled()` awaits
  `document.getAnimations()` rather than sleeping. A 450ms sleep looked fine and
  flickered by 0.234% a run, because the fingerprint grow and the VS pulse are
  both 460ms and start *after* the 160ms blur handler.
- **Nothing uses `fullPage`.** The cage is `position:fixed`; `fullPage` bakes it
  into the middle of the page. It faked a strikethrough on the mobile stance row
  convincingly enough to start a whole investigation. Tall viewports instead.

Tolerance is 0.15% of pixels at a per-channel delta of 14, which absorbs
anti-aliasing differences between machines and still catches any layout shift.

## Invariants the suite enforces

These are what make the tool credible. If a UI change breaks one, the change is
wrong, not the assertion.

- `Σ drawn terms === z₀` — pipeline step 03 and the attribution panel show the
  same sum the model computed.
- `σ(z₀) === reported posterior` — the curve, the crosshair and the verdict cell
  are one number.
- All 1,000 rollouts appear in the step-04 histogram.
- Empirical `p̂` lands within 0.06 of the analytic `P` (they are computed by
  different routes; the settle readout prints both and their difference).
- One threshold drives every label: `<0.58` → INDETERMINATE, `≥0.70` →
  CONVERGED, else LOW SEPARATION. The stamp can never contradict the posterior.
- Unknown fighters are declined (`NOT IN THE INDEX`), never guessed.
- Switch-stance fighters are never labelled orthodox (142 of 2,290 are Switch).

## The palette is not a taste call

```
--bg   #0a0a0c   near-black, not pure black, so glow has somewhere to sit
--blue #2b7fff   BLUE CORNER  (fighter A, left)
--red  #e01a22   RED CORNER   (fighter B, right)
--ink  #f2f2f0   --grey #75757e   --line #1e1e24
```

The original pairing was white-vs-red. Run through a categorical-palette
validator against the `#0a0a0c` surface it **failed two checks**: white has no
chroma so it reads grey, and it sat far outside red's lightness band, meaning
one fighter visually outranked the other before a rollout ran.

`#2b7fff / #e01a22` passes all six: same lightness band, ΔE 32.6 under
deuteranopia, ΔE 39.0 at normal vision, both above 3:1 on the surface. It is
also what the sport paints on the cage, so `BLUE CORNER` / `RED CORNER` are
literally true. Brighter cyans (`#00e5ff`) score better on paper and **fail** the
lightness band at L 0.84 — they shout down the red.

Red means *fighter B* everywhere. Do not reuse it for "leading method",
"selected", or "error" without checking it cannot be read as a corner.

  index.html       THE SOURCE

career versions and the share card lives in **`fightsim/README.md`**. Read it
before touching anything that renders a number.
